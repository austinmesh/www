# Astro 5.18 → 7.2 upgrade notes

Upgraded `astro` 5.18.1 → **7.2.10** and `@astrojs/mdx` 4 → **8.0.0**
(`@astrojs/sitemap` 3.2 → 3.7.4). This covers the breaking changes from both the
[v6](https://docs.astro.build/en/guides/upgrade-to/v6/) and
[v7](https://docs.astro.build/en/guides/upgrade-to/v7/) upgrade guides.

Transitively this also pulls in **Vite 8** (Rolldown), **Zod 4**, and **Shiki 4**.

## What changed

### Content Layer migration (v6 — was blocking the build)

The legacy content collections API was removed in v6, so the build failed
outright before any of this work:

```
[LegacyContentConfigError] Found legacy content config file in "src/content/config.ts".
```

- `src/content/config.ts` → **`src/content.config.ts`**, with `type: 'content'`
  replaced by `glob()` loaders pointed at the existing
  `src/content/pages` and `src/content/projects` directories. **The MDX files
  did not move.**
- `entry.slug` → `entry.id`, `entry.render()` → `render(entry)` in
  `src/pages/[...slug].astro`, `src/pages/projects/[...slug].astro`, and
  `src/pages/projects/index.astro`.
- `z` is now imported from `astro/zod` (importing it from `astro:content` is
  deprecated in v6).
- **Zod 4**: `z.string().url()` → `z.url()`. There is no `.email()` in this repo.
- The fields shared by both collections were factored into a `commonFields()`
  helper, since the schema is a function of the `image` context.

**Why the URLs did not change.** The glob loader's default `id` is generated by
`getContentEntryIdAndSlug`, which does
`segments.map(githubSlug).join('/').replace(/\/index$/, '')` — the exact function
that produced the legacy `slug`. So `about/index.mdx` → `about` and `index.mdx` →
`index` in both APIs, and the existing `entry.id === 'index' ? '' : entry.id`
routing math is unchanged. Verified: all 26 pages build to identical paths.

### v7 — no template changes were needed

- **Rust compiler**: accepted every `.astro` and `.mdx` file with zero errors. No
  unclosed tags, no invalid nesting. This was the biggest unknown going in and it
  turned out to be a non-event.
- **`compressHTML` default `true` → `'jsx'`**: output HTML shrank 492,487 →
  487,252 bytes. All of it is whitespace *between block-level tags*. Spaces
  inside inline text runs (`Compare Devices <svg>`, the footer's
  `See the source at <a>GitHub</a>`) are preserved. **No `{" "}` fixes were
  needed** — see verification below.
- **Sätteri** replaces remark/rehype as the markdown pipeline. This repo has
  **zero** remark/rehype plugins, so `@astrojs/markdown-remark` was not needed and
  `markdown.processor` was left at its default.
- Not applicable here: `src/fetch.ts` (doesn't exist), `@astrojs/db` (not used),
  container renderers (no UI framework), View Transitions internals (not used).

## Things to eyeball in the browser

Low risk overall — the HTML diff was essentially clean — but these are the spots
where something could still look off:

1. **One text change, and it's a fix.** On `/about/meshcore-vs-meshtastic/`, the
   source `"Next-hop"` used to render as `”Next-hop”` (two *closing* curly
   quotes — a smartypants bug, because it sits inside a raw HTML `<td>` in MDX).
   Sätteri now renders it correctly as `“Next-hop”`. Nothing to fix; just be
   aware the character changed.
2. **Scoped-style hashes changed** (`data-astro-cid-ipsxrsrh` →
   `data-astro-cid-wp2l4cmv`) and the CSS chunk was renamed
   `_slug_.css` → `BaseLayout.css`. Both are internal, but they will bust
   any CDN cache on first deploy.
3. **CSS property order** inside scoped blocks is reordered by the new minifier
   (e.g. `list-style:none;padding:0` → `padding:0;list-style:none`). Only
   non-conflicting properties were reordered, so the cascade is unaffected.
4. **`fetchpriority="auto"` is no longer emitted** on `<Image>` output. That was
   always the browser default, so no behavior change.
5. **The `<dialog>` and the `/search/` page** are the only client JS on the site
   and neither was touched — but they're worth a click since Rolldown re-bundled
   the inline script.

## Type-check fixes

`astro check` surfaced two problems, both introduced or exposed by this upgrade.

**1. `commonFields()` had a hand-written image type (2 errors).** I had annotated
the helper's parameter as `() => ReturnType<typeof z.custom<ImageMetadata>>`,
which is not what Astro's schema context actually passes. Under Zod 4 the real
`ImageFunction` returns a `ZodObject`, not a `ZodCustom`, so the two types were
structurally incompatible.

`SchemaContext` / `ImageFunction` are **not** re-exported through the
`astro:content` virtual module — they only exist in
`astro/dist/content/config.d.ts`, which is an internal path I did not want to
import. Instead the helper is now generic over the image schema:

```ts
const commonFields = <T extends z.ZodType>(image: () => T) => ({ ... })
```

It no longer asserts any shape, so the collection's inferred `ImageMetadata` type
flows through untouched.

**2. `onsubmit="return false;"` on the search form (2 hints).** TypeScript
analyses an inline handler's body in a synthetic scope, sees a top-level
`return`, and marks the entire rest of the file unreachable — which is why both
`ts(7027)` hints pointed at unrelated code in the Pagefind script. Confirmed by
removing the attribute and re-running check (2 hints → 0).

Switching to `onsubmit="event.preventDefault()"` traded it for `ts(6385)`
("'event' is deprecated"), because TS resolves the implicit handler parameter to
the deprecated `window.event` global.

The fix was to drop the attribute and bind the listener inside the inline script
the page **already ships**:

```js
input.form.addEventListener('submit', (e) => e.preventDefault());
```

No new script tag, no new JS file, and the event-dialog's intentional inline
`onclick` is untouched — so the CLAUDE.md client-JS constraint still holds. One
behavioral nuance worth knowing: the attribute suppressed submission from parse
time, whereas the listener binds when the inline script runs. The script sits
immediately after the form and executes during parse, so the gap is not
reachable by a user, but it is no longer *structurally* impossible.

## Build timings

Cold cache (`dist`, `.astro`, `node_modules/.astro`, `node_modules/.vite` all
removed), three runs each, same machine:

| | Astro 5.18.1 | Astro 7.2.10 |
| --- | --- | --- |
| Wall clock | 8.48s / 8.15s / 7.86s | 7.37s / 7.03s / **6.76s** |
| **Compile + bundle** | **~1.41s** | **~0.27s** |
| Static route generation | 84ms | 81ms |
| Image optimization (sharp) | 5.78s | 5.50s |

**The compile/bundle phase is ~5× faster** — that is the real v7 win. But end to
end it is only ~14%, because **sharp image encoding is ~88% of this build** and
that code path did not change. If you want the build meaningfully faster, the
lever is images, not the compiler — see the first two recommendations below.

## Recommended opt-ins (none of these are enabled — your call)

Ranked by value for this specific site.

1. **`experimental.incrementalBuild` (7.2)** — the single biggest win available.
   Astro already reuses cached image variants locally (a warm rebuild is ~1.4s vs
   6.8s cold), but Workers Builds starts cold every time and re-encodes all ~296
   image variants on every deploy. Pairing this with a persisted cache directory
   in CI would cut deploy builds substantially.
2. **`image.service.config` (6.1)** — set codec-specific sharp defaults (effort,
   quality) in one place. Directly targets the 5.5s that dominates the build, and
   lets you trade a little file size for encode speed.
3. **`session: false` (7.2)** — this is a fully static site with no sessions.
   Trivially safe, drops the unused session machinery.
4. **`svgOptimizer` (6.2)** — SVGO is no longer hardcoded, so it is now
   configurable. The AISD logos are 28KB/16KB/59KB and are served **as-is**
   (Astro passes SVGs through rather than rasterizing them — this is unchanged
   from v5, so nothing regressed). A tuned optimizer pass would shrink them.
5. **`security.csp`** — worth adopting, *with a caveat*: the event-dialog trigger
   uses an inline `onclick` attribute, which requires `'unsafe-hashes'` in
   `script-src` even with Astro's hashing. 7.1 adds granular directives
   (`script-src-elem`, `style-src-attr`, …) that let you scope that narrowly.
   Budget a little time to get it right rather than turning it on blind.

### Considered and deliberately *not* recommended

- **Fonts API** — nothing to migrate. The site declares no `@font-face` and loads
  no webfonts; it inherits matcha's stack.
- **Live Content Collections (`defineLiveCollection()`)** — this looks like a fit
  for the Discord event rebuild-on-publish cycle, but it **is not**: live
  collections resolve at request time and require on-demand rendering. This site
  is fully prerendered with no adapter, so adopting it would mean giving up the
  static deploy. Keep `scripts/update-discord-event.sh` + the PR workflow.
- **Cloudflare adapter simulation shims** — none to delete. There is no adapter
  installed; this is Workers Static Assets serving prerendered output, not a
  Worker running Astro.
- **`markdown.processor` / `@astrojs/markdown-remark`** — only needed to keep
  remark/rehype plugins. There are none, and Sätteri's output was verified
  equivalent.
- **`paginate()` `format`, `deferRender`, `collectionStorage: "chunked"`,
  `src/fetch.ts` advanced routing** — no pagination, and 24 content entries is far
  too small for the sync-memory options to matter.
